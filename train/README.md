# 学習パイプライン

`index.html` の CPU（本気）が使う方策ネットワークを、自己対戦の強化学習で作るための一式です。
Node.js だけで動きます（外部パッケージなし）。

## 設計の要点

**ゲームのコードを二重に持たない。** 学習側は `index.html` の `ENGINE_START`〜`ENGINE_END` と
`AGENT_START`〜`AGENT_END` の2区画をそのまま切り出して実行します（`harness.js`）。
特徴量の作り方も候補手の作り方も本番と同一のコードなので、学習した方策と
ブラウザで動く方策がずれることが構造的に起こりません。

**行動空間。** 入札は「手札の部分集合」なので組合せが多すぎます。そこで
「いまの最高額 + d を超える最小の組合せ」を d = 1,2,3,5,8,13,21,34 について作り、
これに「降りる」を足した9択に畳んでいます（`agentActions`）。
部分和は動的計画法で一度に表にするので、候補手の生成は1手あたり約1200演算で済みます。

**特徴量（91次元）。** 場のカード、残り山札の内訳（＝全員が見て分かる公開情報）、
自分の小切手の内訳・獲得済みカード・得点、競りの状況、他3人の残金と持ち札、
そして「いま終われば自分が最下位脱落か」といった位置取り。詳細は `index.html` の
`agentFeatures`。

**報酬。** 終局時にのみ与えます。勝ち＝1（同点は山分け）を 0.85、順位を 0.15 の
配分で混ぜたもの。順位を少し混ぜるのは、勝ち負けだけだと信号が疎すぎて
学習の立ち上がりが遅いためです。

**学習法。** PPO（クリップ 0.2）＋ 価値関数の同時学習。相手席は
現在の自分 70% / 過去の自分 20% / 既存の思考ルーチン 10% で混ぜています。
過去の自分を混ぜるのは方策の堂々巡りを防ぐため、既存CPUを混ぜるのは
自己対戦だけで通用する奇妙な均衡に落ちるのを防ぐためです。

## 使い方

```sh
node train/selftest.js    # 部分和DP・候補手・特徴量・先読みの安全性・対局ループの検査
node train/train.js       # 自己対戦で学習（既定 260反復・約45分・4コア想定）
node train/export.js      # train/weights.json を int8 量子化して index.html に埋め込む
node train/verify.js      # 埋め込み後の強さを実測する（先読みあり／なし両方）
node train/widen.js      # 学習済みの網を関数等価に太らせる（容量を増やして続きから学習）
```

主なオプション（`node train/train.js --iters=260 --games=768 --lr=0.0005 ...`）:

| 引数 | 既定 | 意味 |
|---|---|---|
| `--iters` | 260 | 反復回数 |
| `--games` | 768 | 1反復あたりの自己対戦局数 |
| `--workers` | 3 | 対戦を回すワーカースレッド数 |
| `--epochs` / `--mb` | 3 / 1024 | PPOの学習エポックとミニバッチ |
| `--lr` / `--lrEnd` | 5e-4 / 1e-4 | 学習率（線形に減衰） |
| `--ent` / `--entEnd` | 0.02 / 0.004 | エントロピー係数（線形に減衰） |
| `--pCpu` / `--pPool` | 0.10 / 0.20 | 相手席に既存CPU／過去の自分を混ぜる割合 |
| `--evalEvery` | 20 | 何反復ごとに既存CPUと対戦評価するか |
| `--init` | なし | 続きから学習する。`embedded` で `index.html` の埋め込み済み重みから、パス指定で `train/weights.json` から |

学習率は 3e-4 / 6e-4 / 1.2e-3 を20反復ずつ比べ、1.2e-3 は明確に崩れたため
5e-4 から 1e-4 へ減衰させる設定にしています。

## 打ち手の先読み（index.html の agentSearchMove）

方策は「一目で決める」ので、押せば相手が降りるのか返り討ちに遭うのかを確かめていません。
そこで**候補手ごとに局面を複製して実際に打ってみて**、自分の判断どころを2回ぶん読み進め、
その地点の価値を平均して比べます。学習は不要で、既存の重みのまま効きます。

工夫は3つ:

- **山札は複製ごとに切り直す。** 伏せられた順序を覗かないための determinization。
  自己テストで「複製の山札が同じ札束か」「本物の局面が1ビットも変わっていないか」を検査しています
- **打ち切り地点は「自分が判断する局面」にそろえる。** 価値関数はそういう局面でしか
  学習していないため、そこで読むと分布がずれない
- **試行ごとに乱数を全候補手で共通にする**（対応のある比較）。山札の切り方も相手の迷いも
  同じにして手の違いだけを見るので、同じ試行回数でも精度が上がる

実測（対 素の方策3人・互角は0.250）:

| 試行回数 K | 独立な乱数 | 乱数を共通化 |
|---|---|---|
| 4 | 0.341 | 0.398 |
| 8 | 0.375 | 0.428 |
| 12 | 0.418 | 0.390 |
| 24 | 0.380 | — |

乱数の共通化は、試行回数を3倍にするより効きました。K は4以上でほぼ飽和します。

読みの深さ（K=8・各700局）:

| 深さ | 1 | 2 | 4 |
|---|---|---|---|
| 勝率 | 0.375 | 0.443 | 0.449 |

深さ2で利得を取り切るため、既定は **K=12・深さ2** です。ブラウザ実測で1手あたり
中央値6ms（最大78ms）、演出の待ち時間750msに収まります。

## リーグ戦でさらに鍛える（league.js）

`train.js` の自己対戦は「現在の自分」が相手の中心なので、伸びが止まると
そこで頭打ちになります。`league.js` は歴代の王者を溜めたリーグを作り、
**勝ち抜き戦で王座を更新しながら延々と回す**ための道具です。

```sh
node train/league.js --hours=4 --init=embedded      # 4時間ぶん鍛える
node train/league.js --hours=4 --init=train/champion.json   # 続きから
```

やっていること:

1. 挑戦者を「現在の自分 55% ／ 歴代王者 30% ／ 既存CPU 15%」の混成リーグで鍛える
2. 15反復ごとに**王者と直接対決**（1人対3人を両向き・各2000局）
3. 勝ち分の差が `--margin`（既定 0.025）を超えたら**王座交代**。旧王者はプールに残る
4. 交代のたびに「初代（出発点）相手」「既存CPU相手」の勝率も測って記録する
5. 4連敗したら王者の重みに引き戻す（迷走の防止）

既存CPUを15%混ぜているのは、自己対戦だけで固まった方策は「互いに間違えない」前提の
安全策に寄りやすく、**人間の甘い手を咎める力が伸びにくい**ためです。

### 付け入る隙を測る（exploit モード）

```sh
node train/league.js --mode=exploit --target=train/champion.json --hours=0.5
```

対象のエージェントだけを相手に、それを倒すことに特化した方策を鍛えます。
この「専用AI」の勝率が互角（0.250）を大きく超えるなら、対象にはまだ明確な穴があり、
学習を続ける価値があるということです。逆に伸びなければ、
方策の容量や行動空間の側を見直すべき、という判断材料になります。

## 試して駄目だったこと

強くしようとして外した方向も、同じだけ有用な情報なので残します。
いずれも「互角なら 0.250」の物差しで測っています。

**1. 学習量を増やす（league.js）── 効果なし**

リーグ戦の王座交代ゲートは3回連続で横ばい（+0.008 / −0.005 / +0.005）。
さらに王者だけを倒すことに特化した専用エージェントを104反復鍛えても、
勝率は 0.234〜0.247 で互角を超えられませんでした。付け入る隙がほぼ無く、
**この設計のままでは学習量をいくら足しても伸びない**という結論です。

**2. 網を大きくする（widen.js）── 有意な改善なし**

既存の重みを関数等価に太らせて（15,520 → 33,600重み）続きから80反復。
対 既存CPU は 0.554 / 0.574 / 0.571 / 0.553 と振れるだけで、
小さい網の 0.550 から1.5σ以内。容量は制約ではありませんでした。
推論が軽いほど先読みを多く回せるので、小さい網を採用しています。

**3. 先読みの手を方策に教え込む（distill.js）── 明確に悪化**

先読みは方策より強いので、その選択を方策に写せば方策も強くなるはず
（AlphaZero の考え方）── と見込んで実装しましたが、逆でした。

| 目標の作り方 | 一致率 | 新旧対決 |
|---|---|---|
| 硬い最善手 | 0.590 → 0.582 | 0.210 対 0.299 |
| やわらかい評価値分布 | 0.543 → **0.595** | 0.180 対 0.270 |

注目すべきは2行目です。**先読みの真似は上手くなったのに（0.543→0.595）、
実際の強さは落ちました**（0.270→0.180）。1・2の結果と合わせると筋は通ります。
方策の表現力はすでに飽和していて、先読みの強さは「その場で読んで確かめること
自体」に由来します。表現できないものを同じ器に写し取ろうとすれば、
平均的な傾向だけを覚えて元の一貫した戦略を崩すことになります。

`distill.js` は残してありますが（新旧対決に勝ち越した周しか採用しないので
悪化して終わることはありません）、この設計のままでは採用は起きません。
伸ばすなら方策側ではなく、**読みの精度**（価値関数の精度・候補手の作り方・
試行の分散削減）を攻めるのが筋です。

## ファイル

| ファイル | 役割 |
|---|---|
| `harness.js` | `index.html` から ENGINE / AGENT 区画を切り出して Node で動かす |
| `game.js` | 1局を進めて学習サンプルと報酬を取り出す |
| `net.js` | 方策ネットワークの順伝播・逆伝播・Adam・PPO更新 |
| `worker.js` | 自己対戦をワーカースレッドで並列に回す |
| `runner.js` | PPOの1反復（自己対戦→収集→更新）をまとめた土台 |
| `train.js` | 単純な自己対戦での学習 |
| `league.js` | リーグ戦での継続学習／付け入る隙の測定 |
| `evaluate.js` | 席順を回しながらの対戦評価（互角なら勝率0.25） |
| `export.js` | 重みを int8 量子化して `index.html` に埋め込む |
| `verify.js` | 埋め込み後の強さを実測する |
| `widen.js` | 学習済みの網を関数等価に太らせる（net2net widening） |
| `compare.js` | 2つの重みを直接対戦させて優劣を決める |
| `distill.js` | 先読みの手を方策に教え込む反復（効果なし・下記参照） |
| `selftest.js` | ロジックと先読みの安全性の検査 |
| `weights.json` | 学習した重み（float32・リポジトリには含めない） |
