# 学習パイプライン

`index.html` の CPU（ハード）が使う方策ネットワークを、自己対戦の強化学習で作るための一式です。
Node.js だけで動きます（外部パッケージなし）。

## 設計の要点

**ゲームのコードを二重に持たない。** 学習側は `index.html` の `ENGINE_START`〜`ENGINE_END` と
`AGENT_START`〜`AGENT_END` の2区画をそのまま切り出して実行します（`harness.js`）。
特徴量の作り方も候補手の作り方も本番と同一のコードなので、学習した方策と
ブラウザで動く方策がずれることが構造的に起こりません。

**行動空間。** 入札は「手札の部分集合」なので組合せが多すぎます。そこで
「いまの最高額 + d を超える最小の組合せ」を d = 1,2,3,5,8,13 について作り、
さらに **d = 残金の25% / 50%** の2枠を足し、これに「降りる」を加えた9択に畳んでいます
（`agentActions`）。部分和は動的計画法で一度に表にするので、候補手の生成は
1手あたり約1200演算で済みます。

後半2枠が割合なのは、**絶対額の +21 / +34 が完全に死んでいた**からです。学習済みの方策で
9,717判断を数えたところ、この2枠の選択率は 0.000 / 0.000 でした。押しの強さは
「いくら残っているか」に対する相対量で決まるので、固定額の大きな上乗せは
貧しいときは作れず、豊かなときは弱すぎる、という両側から使われない枠になっていました。

**特徴量（91次元）。** 場のカード、残り山札の内訳（＝全員が見て分かる公開情報）、
自分の小切手の内訳・獲得済みカード・得点、競りの状況、他3人の残金と持ち札、
そして「いま終われば自分が最下位脱落か」といった位置取り。詳細は `index.html` の
`agentFeatures`。

**報酬。** 終局時の勝ち＝1（同点は山分け）が本命です。これに順位を混ぜた配分を
`AGENT_SHAPE` で指定しますが、**0.15 から 0 へ線形に焼き鈍します**。順位を混ぜるのは
勝ち負けだけだと信号が疎すぎて立ち上がりが遅いからで、立ち上がりが済んだあとは
「安全な2位」に価値を残す理由がありません（順位1段は 0.15×1/3 = 0.05、
つまり勝率5ポイントぶんの重みがあり、終盤で勝負手を見送る側に効いてしまう）。

**信用割当。** 終局報酬だけだと1席20回以上の判断すべてに同じ数字しか届かず、
どの上乗せが良かったのかを区別できません。そこで他家との**得点差・残金差**を
ポテンシャル Φ とし、中間報酬 `r = γΦ(次) − Φ(今)` を与えます
（potential-based reward shaping）。1局ぶんの合計が Φ(初手)≒0 に畳まれるので
最適方策は変わらず、**信用の配分だけが競りごとに割り振られます**。
優位性は席ごとの判断列に対して GAE(γ, λ=0.95) で積みます。詳細は下の「信用割当」節。

**学習法。** PPO（クリップ 0.2）＋ 価値関数の同時学習。相手席は
現在の自分 70% / 過去の自分 20% / 既存の思考ルーチン 10% で混ぜています。
過去の自分を混ぜるのは方策の堂々巡りを防ぐため、既存CPUを混ぜるのは
自己対戦だけで通用する奇妙な均衡に落ちるのを防ぐためです。

**評価。** 設定を比べるときは**同じ配牌の上で役を入れ替えます**（対応のある比較）。
先読みで「試行の乱数を候補手間で共通化すると試行3倍より効いた」のと同じ原理を
評価側にも使うもので、実測で差のノイズが 1.44 倍縮み、
同じ分解能に必要な局数が半分以下になりました。詳細は下の「評価の対応付け」節。

## 使い方

```sh
node train/selftest.js    # 部分和DP・候補手・特徴量・先読みの安全性・対局ループの検査
node train/train.js       # 自己対戦で学習（既定 260反復・約45分・4コア想定）
node train/export.js      # train/weights.json を int8 量子化して index.html に埋め込む
node train/verify.js      # 埋め込み後の強さを実測する（先読みあり／なし両方）
node train/widen.js      # 学習済みの網を関数等価に太らせる（容量を増やして続きから学習）
```

主なオプション（`node train/train.js --iters=260 --games=768 --lr=0.0005 ...`）:

| 引数 | 既定 | 意味 |
|---|---|---|
| `--iters` | 260 | 反復回数 |
| `--games` | 768 | 1反復あたりの自己対戦局数 |
| `--workers` | 3 | 対戦を回すワーカースレッド数 |
| `--epochs` / `--mb` | 3 / 1024 | PPOの学習エポックとミニバッチ |
| `--lr` / `--lrEnd` | 5e-4 / 1e-4 | 学習率（線形に減衰） |
| `--ent` / `--entEnd` | 0.02 / 0.004 | エントロピー係数（線形に減衰） |
| `--gamma` / `--lam` | 1.0 / 0.95 | 割引率と GAE の λ（`--lam=1` で従来の素のモンテカルロ） |
| `--pot` / `--potM` | 0 / 0 | 中間報酬のポテンシャルの重み（得点差／残金差）。実測で効かなかったので既定は無効 |
| `--shape` / `--shapeEnd` | 0.15 / 0 | 報酬に混ぜる順位の配分（線形に焼き鈍す） |
| `--pCpu` / `--pPool` | 0.10 / 0.20 | 相手席に既存CPU／過去の自分を混ぜる割合 |
| `--evalEvery` | 20 | 何反復ごとに既存CPUと対戦評価するか |
| `--init` | なし | 続きから学習する。`embedded` で `index.html` の埋め込み済み重みから、パス指定で `train/weights.json` から |

学習率は 3e-4 / 6e-4 / 1.2e-3 を20反復ずつ比べ、1.2e-3 は明確に崩れたため
5e-4 から 1e-4 へ減衰させる設定にしています。

`--lam=1 --pot=0 --potM=0 --shapeEnd=0.15` を指定すると、信用割当を入れる前の
学習則と**数値まで一致**します（`selftest.js` で `ret =` 終局報酬・`adv =` 報酬−V を照合）。
A/B を取るときの基準はこれです。

## 信用割当（中間報酬と GAE）

終局にしか報酬が来ない設計だと、**1席あたり20〜25回ある判断すべてに同じ数字が届きます**。
「+1で押した」と「+3で押した」は、その手が現れた局の平均リターンが同じなので、
勾配の上では区別されません。区別を担っていたのはベースライン V(s) だけですが、
学習済みの価値ヘッドを測ると、終局リターンに対する説明力はごくわずかでした。

| 局面 | 価値ヘッドの R² |
|---|---|
| 全体（167,546局面） | **0.049** |
| 競り 1〜3巡目 | **−0.006**（平均を答えるより悪い） |
| 競り 7〜9巡目 | 0.052 |
| 競り 13〜15巡目 | 0.250 |

つまり価値関数は序盤ほぼ無情報でした。これが**先読みの手を方策に教え込む蒸留が
「真似は上手くなったのに弱くなった」理由**とも整合します（下の「試して駄目だったこと」3）。
方策は状態依存の理由を表現できず、平均的な傾向だけを覚えてしまう。

そこで信用の配分を competition の単位に割り振ります。

**ポテンシャル。** `agentPotential`（`index.html`）は他家との**得点差**と**残金差**を
1本の量 Φ に畳んだものです。競り中の札は「まだ失っていない」ので残金に足します
（そうしないと入札そのものが罰になってしまう）。局の開始時は全員同じなので Φ=0 です。

**中間報酬。** `r_t = γΦ(s_{t+1}) − Φ(s_t)`。最後の判断にだけ終局報酬 R を足し、
Φ(終局)=0 とします。すると1局ぶんの合計は `R − Φ(初手) = R` に畳まれるので、
**最適方策は変わりません**（potential-based reward shaping）。変わるのは配分だけです。
`selftest.js` がこの畳み込みを毎回検査しています。

**GAE。** 席ごとの判断列に対して `δ_t = r_t + γV(s_{t+1}) − V(s_t)`、
`A_t = δ_t + γλA_{t+1}` を積みます。λ=1・γ=1・Φ=0 なら `A_t = R − V(s_t)` に戻るので、
従来の学習則はこの設定の特別な場合です。

**先読み側の補正。** ポテンシャルを引いた分、価値ヘッドが学ぶのは「終局報酬 − Φ」です。
先読みは葉の価値で候補手を比べるので、**葉で Φ を足し戻さないと**
「Φ が高くなる手」を不当に嫌います。`agentRollValue` がこれを行います。
報酬の定義（順位の配分・ポテンシャルの重み）は重みと一緒に `AGENT_DATA` に埋め込むので、
学習時と推論時で価値の意味がずれません。

## 評価の対応付け（common random numbers）

先読みでは「試行ごとの乱数を候補手間で共通化すると、試行回数を3倍にするより効いた」
という結果が出ていました。同じ原理は**評価側**にも使えます。

`evaluate.js` は局ごとに種から乱数を作り直すので、**同じ seed を渡した2つの対戦は
同じ配牌・同じ席順から始まります**。カードゲームの分散の主因は配牌なので、
設定を入れ替えた2回を同一シードで走らせるだけで差の分解能が上がります。
（局中は判断が違えば乱数の消費もずれるため、完全な対応にはなりません）

3通りの推定量を、王者と「出力層に σ=0.02 の揺らぎを加えた挑戦者」で比べました。
真の差はほぼ0のペアなので、**差の広がりがそのまま測定ノイズ**です
（各2000局・両向き・くり返し8〜10回。標準偏差の推定自体に±25%程度の幅があります）。

| 推定量 | 差の標準偏差 | 同じ分解能に必要な局数 |
|---|---|---|
| 別シードで両向き（従来） | 0.0121〜0.0126 | 1.00 |
| `duel` 同一シードで両向き | 0.0087〜0.0092 | 0.48〜0.58 |
| `duelField` 相手3席を固定して1席だけ入替 | **0.0085** | **0.49** |

`duelField` は「b だらけの卓に a を1人置いたら、b を置くより勝てるか」を測る形で、
配牌だけでなく**相手の顔ぶれまで共通**になります。リーグ戦のゲートが訊きたいのは
まさにこれなので、ゲートはこちらに変えました。測る量が素直になる副作用もあります
──上の σ=0.02 の挑戦者について `duelField` は −0.005（収束した方策に雑音を足せば
少し弱くなる、という素直な答え）を返しますが、`duel` は +0.003 を返します。
1人対3人を両向きに取ると「3人側も入れ替わる」ので、符号が逆に出ることがあります。

**ゲートの設定を測定値から決め直しました。** 従来の margin 0.025 は実測ノイズの約2.1σで、
**15反復あたり1.2ポイント未満の真の改善は原理的に見えていませんでした**。
対戦は学習より桁違いに軽い（4000局×2で約20秒 ＜ 15反復の学習で約2.5分）ので、
`gateGames` を 2000 → 4000 に厚くし、`margin` は 0.025 → 0.008、
併せて「差が標準誤差の1.5倍を超えること」を条件に加えました。
これで分解能は 2.5ポイント → 約0.9ポイントになります。

なお、この対応付けは**配牌までしか共通化できません**。局中は打ち手の判断が違えば
乱数の消費もずれるので、そこから先は独立に振れます。先読みつきの席を含む比較では
`agentSearchMove` 内部の試行の種も通し番号で進むため、対応はさらに緩くなります。

## 打ち手の先読み（index.html の agentSearchMove）

方策は「一目で決める」ので、押せば相手が降りるのか返り討ちに遭うのかを確かめていません。
そこで**候補手ごとに局面を複製して実際に打ってみて**、自分の判断どころを2回ぶん読み進め、
その地点の価値を平均して比べます。学習は不要で、既存の重みのまま効きます。

工夫は3つ:

- **山札は複製ごとに切り直す。** 伏せられた順序を覗かないための determinization。
  自己テストで「複製の山札が同じ札束か」「本物の局面が1ビットも変わっていないか」を検査しています
- **打ち切り地点は「自分が判断する局面」にそろえる。** 価値関数はそういう局面でしか
  学習していないため、そこで読むと分布がずれない
- **試行ごとに乱数を全候補手で共通にする**（対応のある比較）。山札の切り方も相手の迷いも
  同じにして手の違いだけを見るので、同じ試行回数でも精度が上がる

実測（対 素の方策3人・互角は0.250）:

| 試行回数 K | 独立な乱数 | 乱数を共通化 |
|---|---|---|
| 4 | 0.341 | 0.398 |
| 8 | 0.375 | 0.428 |
| 12 | 0.418 | 0.390 |
| 24 | 0.380 | — |

乱数の共通化は、試行回数を3倍にするより効きました。K は4以上でほぼ飽和します。

読みの深さ（K=8・各700局）:

| 深さ | 1 | 2 | 4 |
|---|---|---|---|
| 勝率 | 0.375 | 0.443 | 0.449 |

深さ2で利得を取り切るため、既定は **K=12・深さ2** です。ブラウザ実測で1手あたり
中央値6ms（最大78ms）、演出の待ち時間750msに収まります。

### 実際にやっているのは「上位2手の決選投票」

`AGENT_PRUNE=0.02`（方策がこれ未満しか推さない手は試さない・ただし上位2手は必ず残す）と
尖った方策の組合せで、**試す候補は平均2.53手しかありません**。9,717判断を数えたところ:

| 試す候補の数 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|
| 割合 | **0.75** | 0.09 | 0.06 | 0.07 | 0.03 |

合法手は平均7.5あるのに、4分の3の判断は2択です。1手あたりの葉評価は約30回。
これで README の観測がつながります ── K=4で飽和するのは**ほぼ二択の問題を解いているから**、
深さ2で足りるのは押した相手が降りるかが2手で分かるから、6msで済むのは30評価だから。

残る2手はたいてい「降りる」と「最小の上乗せ」なので、先読みは**折るか押すかの判断を
精密化しています**。実測でも振る舞いが両極化します（温度0.85）:

| | 素の方策 | 方策＋先読み |
|---|---|---|
| 降り率 | 0.397 | 0.410 |
| 上乗せのうち最小額を選ぶ率 | 0.703 | **0.517** |
| 1回の上乗せ／残金 | 0.115 | **0.152** |

**より折るようになり、押すときはより強く押す。**

### 先読みの利得は終盤に偏っているか（半分だけ当たり）

価値関数の R² は序盤ほぼ0・終盤0.25（上の「信用割当」節）なので、
序盤の先読みは無駄なはずだ、と考えて測りました。素の方策3人相手・各1600局:

| 設定 | 勝率 | 先読み実行率 | 基準比の利得 |
|---|---|---|---|
| 先読みなし | 0.254 ±0.011 | 0% | — |
| 常に先読み | 0.444 ±0.012 | 100% | +0.190 |
| 濃緑2枚目以降だけ | 0.382 ±0.012 | 48% | +0.128（利得の67%） |
| 濃緑3枚目以降だけ | 0.319 ±0.012 | 21% | +0.065（利得の34%） |

終盤の先読みは1判断あたり約1.5倍効率的ですが、**序盤の先読みも利得の3分の1を稼いでいます**。
仮説は外れました。理由は、R² が測っているのは終局リターンに対する**絶対的**な予測力で、
先読みが必要なのは同一局面の**兄弟手の間の順序**だけだからです。候補手間で乱数を
共通化しているので、絶対値に乗った共通のバイアスは差し引かれて消えます。
（「先読みなし」が理論値0.250と一致しているので、計測系は校正できています）

## リーグ戦でさらに鍛える（league.js）

`train.js` の自己対戦は「現在の自分」が相手の中心なので、伸びが止まると
そこで頭打ちになります。`league.js` は歴代の王者を溜めたリーグを作り、
**勝ち抜き戦で王座を更新しながら延々と回す**ための道具です。

```sh
node train/league.js --hours=4 --init=embedded      # 4時間ぶん鍛える
node train/league.js --hours=4 --init=train/champion.json   # 続きから
```

やっていること:

1. 挑戦者を「現在の自分 58% ／ 歴代王者 34% ／ 既存CPU 8%」の混成リーグで鍛える
2. 15反復ごとに**王者と直接対決**。王者だらけの卓の1席だけを挑戦者に入れ替え、
   同一シード＝同じ配牌で 4000局×2 を回す（`duelField`。約20秒）
3. 差が `--margin`（既定 0.008）かつ標準誤差の 1.5 倍を超えたら**王座交代**。
   旧王者はプールに残る
4. 交代のたびに「初代（出発点）相手」「既存CPU相手」の勝率も測って記録する
5. 4連敗したら王者の重みに引き戻す（迷走の防止）

既存CPUを15%混ぜているのは、自己対戦だけで固まった方策は「互いに間違えない」前提の
安全策に寄りやすく、**人間の甘い手を咎める力が伸びにくい**ためです。

### 付け入る隙を測る（exploit モード）

```sh
node train/league.js --mode=exploit --target=train/champion.json --hours=0.5
```

対象のエージェントだけを相手に、それを倒すことに特化した方策を鍛えます。
この「専用AI」の勝率が互角（0.250）を大きく超えるなら、対象にはまだ明確な穴があり、
学習を続ける価値があるということです。逆に伸びなければ、
方策の容量や行動空間の側を見直すべき、という判断材料になります。

## 試して駄目だったこと

強くしようとして外した方向も、同じだけ有用な情報なので残します。
いずれも「互角なら 0.250」の物差しで測っています。

**1. 学習量を増やす（league.js）── 効果なし。ただし一部は測定分解能の問題だった**

リーグ戦の王座交代ゲートは3回連続で横ばい（+0.008 / −0.005 / +0.005）。
さらに王者だけを倒すことに特化した専用エージェントを104反復鍛えても、
勝率は 0.234〜0.247 で互角を超えられませんでした。付け入る隙がほぼ無く、
**この設計のままでは学習量をいくら足しても伸びない**という結論です。

ただし後から測ると、当時のゲート（別シードで両向き各2000局）の**ノイズは 0.012 でした**。
上の3つの差はすべて1σ以内で、「横ばい」と読んだものは**そもそも見えていなかった**
可能性があります。加えて `patience=4` は60反復ごとに重みを王者へ引き戻すので、
遅いが本物の前進は繰り返し捨てられていました。これが「評価の対応付け」節で
ゲートを組み直した動機です。分解能は約0.9ポイントになりました。

もうひとつ、収束後の重みからスケジュール終端の設定（lr 1e-4・ent 0.004）で回すと、
**KL≈0（−0.004〜+0.003）・clip率 0.002〜0.006** で信頼領域がまったく発動しません。
学習の終盤は方策がほとんど動いておらず、「学習量を足しても伸びない」の一部は
「終端スケジュールでは動けない」の言い換えでもあります。

**2. 網を大きくする（widen.js）── 有意な改善なし**

既存の重みを関数等価に太らせて（15,520 → 33,600重み）続きから80反復。
対 既存CPU は 0.554 / 0.574 / 0.571 / 0.553 と振れるだけで、
小さい網の 0.550 から1.5σ以内。容量は制約ではありませんでした。
推論が軽いほど先読みを多く回せるので、小さい網を採用しています。

**3. 先読みの手を方策に教え込む（distill.js）── 明確に悪化**

先読みは方策より強いので、その選択を方策に写せば方策も強くなるはず
（AlphaZero の考え方）── と見込んで実装しましたが、逆でした。

| 目標の作り方 | 一致率 | 新旧対決 |
|---|---|---|
| 硬い最善手 | 0.590 → 0.582 | 0.210 対 0.299 |
| やわらかい評価値分布 | 0.543 → **0.595** | 0.180 対 0.270 |

注目すべきは2行目です。**先読みの真似は上手くなったのに（0.543→0.595）、
実際の強さは落ちました**（0.270→0.180）。1・2の結果と合わせると筋は通ります。
方策の表現力はすでに飽和していて、先読みの強さは「その場で読んで確かめること
自体」に由来します。表現できないものを同じ器に写し取ろうとすれば、
平均的な傾向だけを覚えて元の一貫した戦略を崩すことになります。

`distill.js` は残してありますが（新旧対決に勝ち越した周しか採用しないので
悪化して終わることはありません）、この設計のままでは採用は起きません。
伸ばすなら方策側ではなく、**読みの精度**（価値関数の精度・候補手の作り方・
試行の分散削減）を攻めるのが筋です。

**追記。** 価値ヘッドの説明力を測ったら R²=0.049（序盤は −0.006）でした。
「方策の表現力が飽和している」と書きましたが、より手前に**信用割当の問題**があります。
1席20回以上の判断すべてに同じ終局報酬しか届かないので、状態依存の理由を学ぶ材料が
そもそも無かった。これが「信用割当」節（中間報酬とGAE）を入れた動機です。
蒸留を再評価するなら、まず価値関数の R² が上がったことを確かめてからにすべきです。
